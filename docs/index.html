Disaggregated AI inference over RoCEv2: the KV handoff, end to end

A real small LLM (SmolLM2-135M) runs prefill on one CPU container and decode on another. The KV cache it builds crosses a 2-leaf / 2-spine SR Linux Clos as real RoCEv2 (Soft-RoCE rxe, RDMA WRITE with immediate), and decode continues from it. Numbers come from the captures and counters in outputs/ of this repository. Timings are from a quiet host (the one other heavy container was paused); single runs still vary by tens of percent, so the charts show medians or every run.

Hop by hop: prefill to decode

HopTTL outWhat happens to a RoCEv2 frame
prefill rxe_p64rxe segments the WRITE into 4096 B packets, sets traffic class 0x6a (DSCP 26, ECT(0)), computes the ICRC, sends on eth1 (MTU 9000, offloads off)
leaf1 ethernet-1/10 in63Classifier ROCE maps DSCP 26 to fc3; ECMP hashes the 5-tuple (UDP sport differs per QP) to spine1 or spine2. Ingress discards happen here when rxe bursts faster than the software datapath
spine1 or spine262Single best path to 10.10.2.0/24 via leaf2; egress queue unicast-3 (WRED with ECN 5-20 %)
leaf2 ethernet-1/10 out61Routes onto the decode subnet, queue unicast-3. DSCP 48 (CNP) would use strict-priority unicast-6
decode rxe_dn/aChecks ICRC and PSN, places the payload into the registered slab at RETH VA + offset, consumes a recv WQE on the immediate, returns ACK or NAK

Frames arriving at prefill from decode show TTL 61, confirming three routed hops. Source: outputs/expA-analysis.txt.

Experiment B: correctness (128 tokens)

Does the handoff cost first-token time?

Colocated TTFT is prefill. Disaggregated TTFT is prefill plus whatever of the transfer is still exposed after prefill, so the question is how much network time is left in the critical path.

128-token prompt: prefill + exposed transfer (ms)

512-token prompt: prefill + exposed transfer (ms)

Source: outputs/expC-ttft-128.txt and expC-ttft-512.txt, medians of 5 runs per configuration. x-axis: configuration. Runs vary by tens of percent (colocated 512-token TTFT ranged from 2,701 to 3,956 ms); on a loaded host the same prefill took 4.3 to 7.0 s, which is why the other heavy container was paused. Each segment is its own median, so the bar total (printed above the bar) is not the median TTFT; the median TTFTs are 698 / 1,076 / 1,415 / 812 ms at 128 tokens and 2,773 / 4,427 / 3,394 / 3,225 ms at 512 tokens.

What the numbers supportColocated had the lowest TTFT in 4 of 5 runs at 512 tokens. Bulk push was the slowest in 5 of 5 runs: it adds about 0.3 s (128 tokens, +54 %) and 1.35 s (512 tokens, +60 %) of exposed transfer. Layer-by-layer push hides most of it (exposed 6 to 575 ms) and, with pacing at 300 Mbit/s, is the best disaggregated setup: +16 % over colocated at both lengths. Unpaced layerwise at 128 tokens is worse than bulk because Soft-RoCE retransmission work runs on the same CPU as the forward pass. Splitting prefill and decode is not automatically faster; it pays when the handoff is small compared with the work it separates.

The knob that matters: sender pacing

Exposed transfer (ms) vs the time the pacer allows

Wire bytes / KV bytes

Source: outputs/sweeps.txt, 512 tokens, 23,592,960 B of KV, tc tbf on both workers. x-axis: pacing rate (Mbit/s), "off" is unpaced. Leaf ingress discards in the same order: 962 / 0 / 0 / 0 / 2 / 0 / 31. From 60 to 300 Mbit/s the fabric drops nothing and the transfer takes close to the time the pacer allows (within 15 %). Pacing at 300 Mbit/s beats unpaced: 653 ms against 895 ms exposed transfer, and 24.3 MB against 38.8 MB on the wire. At 400 Mbit/s loss starts again, so the knee is between 300 and 400 Mbit/s. Rate control is what DCQCN or PFC would provide on a real fabric; here there is no ECN, so pacing is manual.

What a faster fabric would change (arithmetic, not measured)

Line-rate time for the handoff alone, no protocol overhead. The measured fabric moves the KV at about 0.2 to 0.7 Gbit/s, which is why the transfer is visible here at all.

What this lab does not testNo GPUs, vLLM, NIXL, UCX, GPUDirect or NVLink. Soft-RoCE on the SR Linux software datapath, so absolute speeds are not representative. No ECN, DCQCN or PFC (zero CE marks). One request at a time, so no incast or multi-tenant interference. A 135M model with 3 KV heads gives a small KV. A shared host: single runs vary by tens of percent. The clabernetes manifest was generated but not deployed.

Reproduce

cd ~/nokia-ai-disagg-inference-lab
bash scripts/fetch-model.sh                  # SmolLM2-135M, once, on the host
sudo containerlab deploy -t topology.clab.yml && bash setup.sh
bash scripts/capture.sh start expA
bash run.sh infer.py --prompt-tokens 32 --wait
bash scripts/capture.sh stop expA
bash scripts/analyze.sh captures/expA.pcap   # totals, conversations, opcodes, DSCP/ECN/TTL
bash scripts/compare.sh 128                  # Experiment B, PASS/FAIL
bash scripts/sweep.sh pacing                 # one sweep group
bash scripts/run-all.sh                      # everything, about 1.5 hours

# useful tshark display filters
udp.dstport == 4791                 # all RoCEv2
infiniband.bth.opcode == 17         # RC ACK / NAK
ip.dsfield.dscp == 26 && ip.dsfield.ecn == 3   # CE marks (none here)
